# 病理演示数据：零种子，走真实 API 造数（v58 车道 C，2576）

> 反驳者原话（2576）：「仓库零病理种子，菜单 169 目标角色 QUALITY 在系统内无任何造数路径，
> 空库时 QUALITY 打开质控页看到的是『报告签发量』30 行全 0 + 另两张『无数据』；
> 要出一条非零数据须 ADMIN 跨 9 页约 18 步、两次登录」。
>
> 回应：**不加种子，加一支驱动脚本** `tools/demo-pathology.py`。它把那 18 步（含两个人的签名）
> 全部走真实 API 做一遍，落下的每一行都是系统自己写的；ADMIN 一条命令，QUALITY 打开质控页就有数。

## 一、为什么仓库里没有病理种子（而且以后也不会有）

1. **零回填 / 零伪造种子是本仓铁律**。`docs/种子数据分层清单.md` §C 明写：演示数据从第一天起就走脚本不走迁移，
   43+ 个迁移里不存在 C 类数据；生产库禁止出现演示数据。
2. **一条 insert 出来的「已签发报告」不是数据，是一张画出来的表**。它没有取材记录、没有蜡块与切片、
   没有两个人的签名（`first_signer_id ≠ second_signer_id`）、没有 `path_process` 流转节点、
   `outp_order` 也不会被置成 EXECUTED——质控页的 16 条指标里一半会因为缺这些列而对不上账，
   反而制造出「表里有报告、穿透明细里没人签过」的自相矛盾。
3. **病理号是法定编号**，由 `PathologyRegistryController` 按配置规则生成（实测 `2026-C-000001` 起），
   种子里手写病理号会撞规则、撞唯一索引，或者把序号烧掉。

所以合法解法只有一种：脚本做真实业务操作。脚本本身**不连数据库、不 import 任何 DB 驱动**，
只用 `tools/e2elib.py` 的 HTTP 调用；调用形态逐字抄自 `tools/e2e-v48-pathology.py` 与
`tools/e2e-v57-audit.py`（两套已在 CI 全新库上跑通），不猜契约。

## 二、脚本怎么跑

### 前提

- 后端已启动（任一 profile；下文以 dev 为例），`admin/admin123` 可登录
  （或用环境变量 `HIP_E2E_USER` / `HIP_E2E_PASSWORD` 指定一个 ADMIN 账号——建患者、排班、开单、结算、
  病理全流程都要 ADMIN 兼有的角色）。
- 主数据里有名字含「病理」或「活检」的收费项目（B 类种子 `组织病理学检查(活检)` 随 Flyway 自带；
  被实施替换掉时脚本会明确报「主数据缺项，非功能缺陷」）。
- Python 3（标准库即可，无第三方依赖）。

### 命令

```bash
# 默认：5 个阶梯标本 + 1 个拒收 = 登记 6 个，打印逐步日志 + 汇总表 + 质控页有数清单
HIP_E2E_BASE=http://localhost:8080/api python tools/demo-pathology.py

# CI / 只要一行结论
python tools/demo-pathology.py --count 2 --quiet

# 指定实例与数量
python tools/demo-pathology.py --base http://localhost:8083/api --count 8
```

| 参数 | 含义 |
|---|---|
| `--count N` | 阶梯标本数，默认 5。N 个标本从阶梯**顶端往下**轮流分配（先「双签已签发」、再「已诊断未签发」……），保证 N=1、2 时也有已签发报告与蜡块；另**固定再加 1 个拒收标本**，故实际登记 N+1 个 |
| `--quiet` | 只打印一行成功摘要；任何一步失败打印响应并以非 0 退出 |
| `--base` | API 根地址，默认读环境变量 `HIP_E2E_BASE`，再默认 `http://localhost:8080/api` |

退出码：`0` 成功；`1` 任一业务步骤失败（打印「FAIL 步骤「xx」：<响应>」）；
`2` 造完数后质控概览三项（登记总量 / 蜡块产出 / 报告签发量）仍有 0——「造了数但质控页看不见」正是 2576 要钉死的。

### 阶梯分布（`--count 5` 默认）

| 序号 | 目标状态 | 走到的步骤 | 附加 |
|---|---|---|---|
| 1 | 双签已签发 | 登记 → 核收 → 取材 2 块 → 脱水篮 → 包埋 → HE 切片 2 张 → 染色 → 诊断 → 初签（admin）→ 复签（demo_pathdoc）→ 签发 | IHC 医嘱（CK7）挂接 2 张切片并完成；特殊染色医嘱（PAS）带原因取消；补充报告 1 份 |
| 2 | 已诊断未签发 | 同上到「诊断」为止 | |
| 3 | 已切片已染色未诊断 | 同上到「染色」为止 | |
| 4 | 已核收未取材 | 登记 → 核收 | |
| 5 | 已登记未核收 | 登记 | |
| 6 | 已拒收 | 登记 → 拒收（原因必填；不删行、不改 status） | |

`--count` 大于 5 时从第 6 个起重新从顶端轮流；三个附加动作轮流分配到各「已签发」标本上（只有 1 个已签发时三者都落在它身上）。

### 可重复跑

- 所有患者名带毫秒时间戳后缀（`演示病理01号33865321`），同一实例反复跑不撞名；每跑一次登记总量 +N+1。
- 复诊医师账号 `demo_pathdoc`（DOCTOR_OUTP）与质控账号 `demo_quality`（QUALITY）幂等复用，
  口令沿用 `tools/e2elib.py` `provision_user` 的 E2E 约定；账号已存在且口令不符时脚本会在「建…账号」一步失败，属环境冲突而非功能缺陷。
- 已挂进 CI：`.github/workflows/ci.yml` e2e 作业在 `e2e-v57-audit.py` 之后跑 `demo-pathology.py --count 2 --quiet`，
  之前的 37 套 E2E 造的病理数据与它互不干扰（实测：先跑本脚本两遍再跑 v48 / v57 两套，全部通过；
  `/pathology/pending` 排除已登记的申请，v48 的 `pend[0]` 不会捞到本脚本的申请）。

## 三、跑完之后：QUALITY 角色到哪个菜单看什么

1. 用 `demo_quality`（脚本建的）或 `bootstrap-demo.py` 的 `quality01` 登录。
2. 左侧菜单 **门诊业务 → 病理质控**（`sys_menu` 169，路由 `/pathology/qc`，V156 授权 ADMIN + QUALITY；
   同级的 168「病理工作台」QUALITY 没有授权，那是 TECHNICIAN / DOCTOR_OUTP 的）。
3. 页面默认统计区间是**近 30 天**（`GET /api/path-qc/indicators` 不传起止即此窗口）。跑完 `--count 5` 实测（2026-09-09，空库首跑）：

## 四、脚本做不到的事（如实写，不吹）

- **不能回溯日期**。所有时刻都是运行当下（服务端 `now()` / `Instant.now()`），脚本没有任何「把 collected_at 改成上周」的手段——
  那本身就是回填。因此：30 天趋势图只有「今天」这一根柱；`WORKLOAD_REPORT` 的另 29 行仍是 0；
  报告及时率 100%、各环节 TAT 0.0 小时都是「几秒内走完」的演示值，**不代表任何科室的真实水平**。
  想要多天的柱子，只能多天各跑一次。
- **只造门诊来源、ROUTINE 类型、非加急的标本**：`inp_source=0`、`frozen/cytology/consult/molecular=0`、`urgent=0`，
  `REPORT_FROZEN` 无行。这些分支各自有真实业务前置（住院医嘱、冰冻申请），不在本脚本范围。
- **不会让三条符合率有数**（见上表）。
- **时钟**：`collected_at` 由数据库 `now()` 落，`received_at` 由应用 `Instant.now()` 落。数据库与应用不在同一台时钟上时
  （本机 WSL 里的 PostgreSQL + Windows 上的 JVM，实测相差约 0.8 秒），`SPECIMEN_RECEIVE` 会出现 `negative_interval` 非零——
  这是部署环境的时钟问题，CI（同一 runner）与正常部署（同机或 NTP 对时）不会出现。
- 需要 ADMIN 权限，且会创建 `demo_pathdoc` / `demo_quality` 两个演示账号（幂等）。生产库不要跑——它是演示脚本，
  与 `bootstrap-demo.py` 同属 C 类。
