# 采购需求覆盖盘点与下一步规划（v3）

> 基准：《采购需求》107 模块 / 4298 条技术参数 ｜ 更新：2026-08-04（一至十二期完成后）
> 现状：12 后端模块、16 Flyway 版本、36 页面、9 套 E2E + 22 测试、CI 全绿

## 一、判断：从「广度铺设」转向「深度达标」

十二期后，107 项中纯软件可推进的约 60 项已全部 MVP 覆盖。但采购需求的验收单位是 **4298 条技术参数**而不是模块数——MVP 与「完全响应」之间存在系统性差距。同时，真实医院上线所需的工程配套（单据打印、报表导出、等保安全、数据迁移）尚未建设。**下一阶段不再新增业务广度，转向三条线：落地就绪、医技本体自建、验收达标。**

## 二、下一步规划

### 第十三期「落地就绪」（建议下一步）
医院真实运转的最后一公里，全部无外部依赖：

1. **单据打印**：挂号凭条、处方笺（含审方签名栏）、收费票据、检验报告单、出院结算单——打印友好的 HTML 模板 + 浏览器打印
2. **报表导出**：日结报表（收费员轧账）、科室工作量、Excel/CSV 导出
3. **等保三级基线**：操作审计日志（谁在何时改了什么）、密码策略（复杂度/有效期/锁定）、会话超时、登录日志
4. **按钮级权限**：perm 权限点落到前端指令（v-perm）与后端注解
5. **工程还债**：九至十二期 JdbcTemplate 控制器下沉独立模块；E2E 纳入 CI（Actions 起完整后端）

### 第十四期「医技本体自建」
纠正一个此前的归类：LIS/RIS 的**系统本体是纯软件**，设备只是输入源之一：

1. **LIS 本体(56)**：申请单 → 采样打码 → 标本核收 → 结果录入（手工双通道 + 已有 MLLP 设备通道）→ 双审核 → 发布（现有危急值/报告链路复用）
2. **RIS 本体(62)**：检查登记 → 分诊到机房 → 报告书写（所见/所得模板）→ 审核发布
3. **PACS 起步(63)**：对接开源 Orthanc（WSL 部署），影像上传/WEB 调阅，云胶片(41)链接生成
4. **心电(4)基础**：心电报告录入与归档（设备接入走 MLLP 预留）

### 第十五期「专科表单与移动端」
1. **手术麻醉(54)基础**：手术申请 → 排台 → 术中记录单 → 麻醉记录
2. **ICU(55)基础**：重症护理记录单（每小时体征密集录入，复用体征模型）
3. **移动医护(60/61)**：现有前端 PWA 化（离线缓存 + 移动布局），查房开嘱/床旁执行
4. **电子病历结构化深化**：病历模板管理（科室级段落模板）、病程记录续写体验

### 第十六期「验收达标冲刺」
1. **4298 参数覆盖矩阵**：逐条建立「符合/部分/未覆盖」台账（投标与验收的硬文档）
2. **数据迁移工具箱**：老系统患者/费用/库存导入模板与校验脚本
3. **性能压测基线**：挂号/收费并发压测报告（对标需求性能条款）
4. **部署与文档**：生产部署手册（docker compose 一键）、分角色操作手册、培训材料

### 外部条件到位即插入（不占期序，接入点已备好）
医保 SDK（InsuranceAdapter）、CA 厂商（SignatureAdapter）、微信公众号（portal H5 嵌入）、LIS/PACS 设备直连（MLLP 2575）、AI 阅片/CDSS（Python 子服务位）、电子健康卡（省平台）。

## 三、优先级依据

- **第十三期最优先**：没有打印和日结，收费窗口一天都跑不下去；没有审计和密码策略，过不了等保测评——这些是「能否真实上线」的门槛，而非功能锦上添花
- **第十四期**把此前误判为「需设备」的 LIS/RIS 本体拿回来自建，是采购清单中含金量最高的剩余大项
- **第十六期**直接服务投标/验收动作，产出的是文档与工具而非功能
