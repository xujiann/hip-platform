# 采购需求覆盖盘点与下一步规划（v4）

> 基准：《采购需求》107 模块 / 4298 条参数 ｜ 更新：2026-08-04（一至十六期完成后）
> 现状：12 后端模块、17 Flyway 版本、44 页面、10 套 E2E + 22 测试、CI 全绿、压测基线 92.6 req/s

## 一、终盘点

**已覆盖**：107 项中软件可实现项全部 MVP+ 落地（门诊/住院/药事/医技 LIS-RIS 本体/护理质控/患者管理/HRP/数据中台/集成引擎/CDR/患者端），并具备落地配套（打印、日结、等保基线、迁移工具、压测、部署手册）与验收工具（4062 条参数矩阵 CSV）。

**未覆盖，分三类**：

1. **外部条件项**（接入点已预留，等条件）：医保 SDK、微信公众号/APP 资质、CA 厂商、LIS/PACS/超声/内镜/心电设备直连、AI 算法、电子健康卡省平台、DRG 官方分组器
2. **仍可自建项**：PACS 影像服务（开源 Orthanc）、全文检索（OpenSearch）、CDA 标准文档输出、CDC 增量同步、AI 子服务骨架
3. **非编码工作**：4062 条参数逐条评定、分角色操作手册、培训材料、试点实施

## 二、下一步计划（第十七期起）

### 第十七期「质量工程与架构还债」← 建议下一步
业务铺设结束后的第一优先级是让存量代码可长期维护：

1. **聚合层下沉**：九至十六期的 JdbcTemplate 控制器（护理质控/患者管理/HRP扩展/数据治理/医技本体）按域下沉为独立 Maven 模块 + JPA 实体，消除 server 模块巨型化
2. **测试补强**：合理用药规则、审方状态机、LIS 流转、密码策略等关键逻辑补单测（目标 50+ 用例）
3. **E2E 进 CI**：Actions 第三 job 起完整后端（postgres 服务容器 + jar）跑核心 E2E 两套
4. **静态检查**：checkstyle/spotless 进 CI，统一代码风格

### 第十八期「标准与互操作」
1. **CDA 文档输出**：CDR 文档 → WS/T 500 样式 XML 生成器（互联互通测评的文档规范基础）
2. **全文检索**：WSL 部署 OpenSearch，CDR 文档索引化，病历全文检索页升级
3. **轻量 CDC**：CDR 抽取从全量改为 updated_at 水位增量，为数据量增长做准备

### 第十九期「影像与 AI 子服务（自建可行部分）」
1. **PACS 起步**：WSL/容器部署 Orthanc，DICOM 上传与 Web 调阅，检查报告关联影像链接（云胶片雏形）
2. **AI 子服务骨架**：按总体规划建 Python FastAPI 子服务（mock 阅片评分/CDSS 建议接口），主平台适配器接入——真实模型到位即插即用

### 第二十期「验收与实施冲刺」（以文档与评定为主）
1. **参数矩阵评定**：4062 条按 8 大域分批，AI 辅助初评 + 人工复核，产出正式《技术偏离表》
2. **分角色操作手册与培训课件**（医生/护士/收费/药房/管理员）
3. **试点实施演练**：真实老系统数据脱敏迁移演练 ×2 轮、切换预案

### 外部条件触发项（随时插入）
条件到位即启动对应对接战役——医保（InsuranceAdapter）、CA（SignatureAdapter）、设备（MLLP 2575）、微信（portal 嵌入）、AI（Python 子服务位）。

## 三、判断依据

- 平台功能面已足以支撑试点，**此刻最大的风险不是缺功能，而是快速堆积的代码在无还债情况下继续生长**——因此十七期还债优先
- 十八期对准互联互通测评（CDA 是文档规范核心），十九期把「需设备」中可自建的软件部分先立起来
- 二十期性质是交付工程而非开发，宜与医院方联合推进
