## 总体判断

上轮修复中，条件更新家族与报表只读角色确实生效（见文末"已确认修得正确"），
但**有六项修复本身存在缺陷，其中两项完全没生效、一项把问题换成了更糟的形态**（见 C 组）。
另有三类新的系统性问题：

1. **修复没有覆盖真实部署路径**——1.0.6 的两道安全闸门绑定 `pilot/prod` profile，
   而部署编排从不设 profile，闸门在按文档部署时全部跳过。**清单标 ✅ 但实际未生效，比未修更危险。**
2. **权限补丁按控制器逐个打，漏了整片**——1.0.6 补了 6 个控制器，但打印/日结、CDR 调阅、
   HRP 八个控制器（含工资批量覆写）仍然零权限。
3. **前端从未被审计过**——脱敏值回写破坏真实数据、blob 下载 100% 失效、
   资金操作大面积无防重、路由零角色守卫。

**C 组关联风险**（非 bug 但需决策）：

- **触发器放大与锁序反转**：V50 的 `trg_outp_order_touch_reg` 使 outp_order 的每次写都 update 挂号行，
  `claimCharge/claimDispense/claimRefund` 的 N 行批量更新被放大成 N 次同行更新；且收费/发药是
  order→registration，医生站保存诊断是 registration→order，**存在死锁面**（需压测确认）
- **报表引擎从 PreparedStatement 退回 Statement**（`DataStdController:178`）：驱动层不再拒绝多语句，
  唯一防线是 `contains(";")`；`FORBIDDEN_KW` 无 `commit|rollback|begin|discard|reset`，
  一旦分号过滤被绕过，`commit;` 即可脱掉 `set local role` 沙箱。建议改回 PreparedStatement
- **profile 判断散落三处**（JwtService / MockAdapterGuard / PortalController.confirmPay 各写一份）——
  与 A-1 叠加：任何不经 `spring.profiles.active` 的部署方式让三道闸门同时静默失效。应抽 `HipProfiles.isProduction()`
- **住院侧医保冲销整体缺失**：全仓只有 `ChargeService.refund` 调 `reverse()`——
  **P1-14/15 只修了门诊那一半**，住院退费/重结算不回退年度起付线与统筹额度
- **`applyPathway` 的 catch 是地雷**：`@Transactional` 内 catch DuplicateKeyException 后正常返回，
  能 work 只因 catch 之后再无 SQL；后人补一条审计写入就会撞 25P02（与 C-1 同根）
- **皮试类别用 `Map.of`**：迭代顺序不确定；且收紧后历史 `drug_name='皮试液'` 这类通用名记录会被判无同类阴性结果，
  对应输液全部被 4502 挡住——**上线前需清点存量**
- **序列取号触发全会话 flush**：`nextGroupSeq()`/`nextInSeq()` 用未声明 query space 的原生查询，
