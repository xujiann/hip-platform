# HIP 标准化产品方案（v1，2026-08-06）

> 目标：把现平台从「面向峨眉山市人民医院的单院系统」升级为**同级别同类医院（县市级综合医院）可复用的标准产品**；
> 每家医院实施时按个性化需求做实施层开发，**不分叉核心代码**。

## 一、总原则：配置优先，扩展次之，禁止分叉

个性化需求的实现优先级：**改配置 > 换数据 > 实现 SPI > 实施层扩展模块**；任何情况下不 fork 平台核心代码。
每家医院 = 标准产品（同一构建产物）+ 该院的配置与数据 + 少量实施层扩展。

## 二、四层标准化模型

| 层 | 内容 | 变更主体 | 现状 |
|---|---|---|---|
| 1 标准产品层 | 12 后端模块 + 前端 65+ 页 + Flyway V1-V999 + 必需字典 | 产品团队，随版本发布 | ✅ 已具备（需种子分层） |
| 2 配置层 | sys_config（院名/比例/开关）、科室病区床位、角色菜单、字典（药品/收费/ICD）、规则库（CDSS/DRG/医保对照/审核）、报表引擎 | 实施工程师，纯数据 | ✅ 机制已全 DB 化，缺初始化工具 |
| 3 扩展层（SPI） | InsuranceAdapter（省医保各异）/ PayAdapter（聚合支付商各异）/ SignatureAdapter（CA 各异）/ int_adapter 路由（LIS 设备各异）/ ai-service HTTP | 按地区/供应商做实现包，可跨院复用 | ✅ 接口已定义，各有 Mock |
| 4 实施定制层 | 该院独有的页面/接口/报表，独立 Maven 模块 + Flyway V10000+ 段 | 实施项目组 | ⬜ 机制待建 |

**多院形态**：单院独立部署（每院一实例一库）。不做多租户 SaaS——县市级医院独立法人、等保数据边界、院内网部署形态都指向单实例；标准化收益来自「同一产物+分层配置」，不来自共库。

## 三、差距清单（现状 → 产品化要做的事）

1. **种子数据分层**：31 个迁移里字典种子与演示数据混排。拆三类：
   - A 平台必需（菜单/角色/默认参数/数据元/术语框架）——留 Flyway
   - B 行业基线（ICD-10 简表/给药途径/班次/CDSS 与 DRG 示例规则）——独立「标准字典包」，init 工具导入，实施时可换院方目录
   - C 演示数据（患者/排班/体检套餐）——只进 bootstrap-demo，生产不装
   历史迁移不改（Flyway 纪律），以「新库初始化路径」实现分层：V1-V39 照跑 + init 工具负责 B/C 的装与不装
2. **医院初始化工具** `tools/init-hospital.py`：交互/配置文件驱动——院名与品牌、科室病区床位结构、8 角色账号、启用模块清单、字典批量导入（药品/收费项目 CSV 模板）；替代 bootstrap-demo 的生产版
3. **功能开关（模块级）**：医院未购/不用的模块（如 ICU/体检/科研）可关。落地：sys_config `module.<name>.enabled` → 菜单树过滤（已 DB 化，摘菜单即隐藏入口）+ 后端对应 Controller 按开关 404（`@ConditionalOnProperty` 或过滤器统一拦截）
4. **实施层扩展机制**：约定 `impl/<hospital>` Maven 模块模板（依赖平台 jar，Spring 自动扫描 `cn.hip.impl.*`）；Flyway 版本段规约：平台 V1-V999，实施 V10000+；前端实施页面走独立路由前缀 `/impl/*` 懒加载
5. **版本与发布工艺**：语义化版本（平台 1.x.y）；发布物 = server jar + 前端 dist + compose + 升级说明；升级 = 停服→备份→换 jar/dist→Flyway 自动前滚；做一次 N-1→N 升级演练进 E2E
6. **品牌与文案配置化**：院名已参数化；补 logo、主题色、打印页眉落款进 sys_config
7. **实施工艺包（文档）**：实施 checklist（装机→初始化→字典→接口适配→培训→试运行）、接口现状调研表（医保/LIS 设备/PACS/CA）、配置手册（全部 sys_config 键注释成册）

## 四、分期计划

### 产品化一期「标准版可装第二家医院」（✅ 已完成，2026-08-06，提交 5091741）
1. ✅ 种子数据三类分层（docs/种子数据分层清单.md，确认迁移无 C 类演示数据）
2. ✅ `init-hospital.py` + 字典 CSV 模板 + 三个实施 API（药品/收费导入、床位批量创建）
3. ✅ 模块级功能开关（ModuleGate 六模块注册表，菜单过滤 + API 404 双路，V43）
4. ✅ 安全基线并入（HIP_JWT_SECRET 环境变量、init 强改 admin 口令）；品牌扩展键走 extraConfig
5. ✅ ADR-0003 实施定制层规约 + impl/template-hospital 可编译模板（V10000 段示例）
> 验收：全新库装机演练通过（换院名/关模块 404/建科室床位/导字典/换口令）；55 测试 + 19 套 E2E

### 产品化二期「发布与实施工艺」（工程+文档）
1. 发布打包脚本 + CHANGELOG + 语义化版本起点（定 1.0.0）
2. 升级演练：从上一版备份库前滚到新版，进 E2E/CI
3. 实施工艺包三件套（checklist/调研表/配置手册）

### 产品化三期「虚拟第二医院实施演练」（验证闭环）
用一个虚拟医院做全流程实施彩排：不同院名与科室结构、关闭 2-3 个模块、导入一套不同字典、写一个 impl 示例模块（含 V10000 迁移 + 一个定制页）+ 一个假医保适配器实现。
全量 E2E 在该实例复跑 → **通过即证明「标准产品 + 实施个性化」路径成立**。

### 与 v15 的关系
峨眉山即产品的**第一个实施案例**：v15 方向 B/C（试点上线与运行）继续走，其配置与定制沉淀反哺产品化一期的分层清单。顺序建议：v15-B 安全基线 → 产品化一期 → v15-C 试点 与 产品化二三期并行。
