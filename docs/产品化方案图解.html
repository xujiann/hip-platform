HIP · Hospital Information Platform

标准化医院信息平台 · 图解说明

把面向单家医院的信息系统，升级为同级别同类医院（县市级综合医院）可复用的标准产品； 每家医院实施时按个性化需求做实施层开发，标准核心永不分叉。

1总原则：一条不变式

标准化不是把系统做「通用」，而是把「每家医院的不同」安放到正确的层里。

不变式：每家医院 = 同一个标准发布产物 + 该院的配置与数据 + 少量实施层扩展。
个性化落地优先级：改配置 > 换数据 > 实现 SPI > 实施扩展模块；任何情况下不 fork 平台核心代码。

这条不变式成立的前提，是平台已经具备三个「标准化基因」：机构参数全部走 sys_config、菜单/角色/规则库全部数据库化、对外差异点全部收敛为适配器接口（SPI）。 这些能力在现平台已存在，产品化的工作是把它们制度化并补齐工具链。

2四层标准化模型

越往下越稳定、随产品版本演进；越往上越灵活、随医院实施变更。升级只动下层产物，不破坏上层内容。

层内容变更主体现状
L1 标准产品12 后端模块、前端 65+ 页、Flyway V1–V999、必需字典产品团队，随版本发布已具备
L2 配置sys_config、组织结构、角色菜单、字典、规则库、报表引擎实施工程师，纯数据机制已全 DB 化 缺初始化工具
L3 SPI 扩展医保 / 支付 / CA / 设备路由 / AI 服务五类适配器按地区、供应商做实现包接口已定义含 Mock
L4 实施定制该院独有页面 / 接口 / 报表，独立模块实施项目组机制待建

3部署形态：一院一实例

标准化的收益来自「同一产物 + 分层配置」，而不是共享数据库。

4个性化需求的处置决策

每一条个性化需求进来，按同一条决策链落到四层中的某一层——链条末端不存在「改平台核心」这个选项。

5标准产品层：模块地图

L1 的构成：四个平台底座模块支撑八个业务域模块，server 聚合装配，前端单壳承载全部页面。

6配置层：数据即个性化

医院之间 80% 的差异是数据形态的差异。配置层回答两个问题：哪些东西是数据？新医院第一天怎么把它们装进去？

6.1 种子数据三类分层

现平台 31 个迁移中字典种子与演示数据混排，产品化后按去向分三类。历史迁移不改（Flyway 纪律）， 分层通过新库初始化路径实现：平台迁移照跑，B/C 两类由工具决定装或不装。

6.2 模块级功能开关

医院未采购或暂不使用的模块（如 ICU、体检、科研）需要能整体关闭。开关是一份配置、两处生效——只藏菜单不拦接口是伪关闭。

7SPI 扩展层：换实现不换平台

对外对接是医院间差异最硬的部分——各省医保、各家支付商、各厂 CA 与设备，接口互不相同。平台把每一类差异收敛为一个接口，实施时只替换实现。

8.3 实施定制模块规约

  • 代码位置：impl/<hospital> 独立 Maven 模块，依赖平台 jar，包名 cn.hip.impl.* 由启动器自动扫描；
  • 数据库：仅 V10000+ 段迁移，只建 impl_ 前缀自有表；需要平台数据时读平台表、写自己的表；
  • 前端：定制页面走 /impl/* 路由前缀，懒加载，独立目录，不改平台页面源码；
  • 发布：标准产物 + impl 模块 jar 同机部署；平台升级时 impl 模块随编译验证兼容性。

9实施工艺：从装机到试运行

标准产品的价值最终由实施工艺兑现：一条可重复的流水线，每一步有工具、有产物、有退出条件。

实施工艺包（随产品交付的文档件）

  • 实施 checklist：从装机到上线逐项打勾，每项带退出条件；
  • 接口现状调研表：进场首日摸底医保 / LIS 设备 / PACS / CA 现状与联系人；
  • 配置手册：全部 sys_config 键、字典模板、角色矩阵成册；
  • 操作培训脚本：8 角色 + 患者端（已具备，docs/培训脚本.md）。

10产品化路线图

三期递进，每期一个可验证的出口；峨眉山试点并行推进，实施经验反哺分层清单。

验收口径

  1. 同一发布产物在两个「医院」实例上运行，无任何代码分叉；
  2. 第二家医院从裸机到可培训 ≤ 1 人日（不含外部接口联调）；
  3. 关闭模块后菜单与接口双失效，E2E 断言通过；
  4. N-1 → N 升级演练：备份→前滚→回归全绿，实施段迁移无冲突；
  5. 全量 18 套 E2E 在虚拟第二医院实例复跑通过。
