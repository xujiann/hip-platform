## 平台自身混用两个时钟源写同一条时间线（v63 记）

**现象**：`path_process.occurred_at` 由**库端 `now()`** 落（`PathologyProcessController.logProcess`），
而 RECEIVE 节点那一行由**应用侧 `Instant.now()`** 落
（`PathologyRegistryController` 接收核对：`jdbc.update(... , Timestamp.from(received), ...)`，
同一个值也写进 `path_specimen.received_at`）。两者是**两个时钟**。

**怎么暴露的**：v62 定版跑全新库全量 E2E 时 `e2e-v58-audit.py` 假红一次——
`lastNode` 期望 `TECH_CANCEL`、实得 `RECEIVE`。查库发现 RECEIVE 的 `occurred_at` 比其后**所有**流转节点晚约 1 秒。
实测本机 WSL 与 Windows 的时钟在漂（同一天内从 +0.96s 摆到 -0.06s 又到 -0.56s），
而 `/trail` 的 `lastNode` 取 `order by pr.occurred_at asc, pr.id asc` 的最后一行，于是 RECEIVE 排到了最后。

**为什么 CI 不会暴露**：CI 里应用与 PostgreSQL 在同一台机器、同一个时钟，两个来源恒等。

**为什么这是真债而不只是本机环境问题**：多医院部署操作指南给的就是**应用与库分机部署**的形态。
一旦两台机器有秒级时钟差（NTP 未配或漂移），就会出现：
流转轨迹里 RECEIVE 排在取材之后、`hours_from_receive` 为负、`hours_since_prev` 错位、
按「最近一次活动」判停滞的 `/anomalies` 误报。表现是数据错乱而不是报错，很难从现场反查。

**处置方向**（未做，留给后续轮次）：
- 要么把 RECEIVE 这一行也改成库端 `now()`（但「接收时刻」允许补录历史值，不能一律用 now()——
  需区分「用户补录的业务时刻」与「系统记录的发生时刻」，可能要拆成两列）；
- 要么在写入前做一次时钟偏移校正（应用侧读一次库端 `now()` 求差）。
- 无论哪种，`/trail` 的排序与 `hours_*` 计算应当明确它依赖的是哪一个时钟。

**现有线索**：`PathologyRegistryController` 已有 `CLOCK_SKEW_SECONDS` 常量（用于「接收时刻不能晚于当前时刻」的容差），
说明这个问题此前被局部意识到过，但只用在校验上，没用在排序与时长计算上。

## HRP 资产编号靠 nanoTime 取模生成，撞号即 4091（v64 记）

**现状**：`modules/hrp/src/main/java/cn/hip/hrp/web/AssetController.java` 建资产时
`assetNo = "ZC" + 当日日期 + "-" + System.nanoTime()`。v64 之前是 `System.nanoTime() % 100000`。

**那个取模为什么会撞**：Windows 上 `System.nanoTime()` 走 QueryPerformanceCounter，
常见 10 MHz 频率使返回值恒为 100 的整数倍，于是 `% 100000` 的可能取值只有 **1000 个**（不是十万）。
一次 E2E 建十来个资产，生日碰撞概率约 4–5%——2026-09-17 的全新库全量 E2E 就是这么红的：
`hrp_asset_asset_no_key` 唯一约束冲突 → 全局兜底 4091「数据不符合约束要求」，
而那句话既不说是哪个字段、也不说是撞号，运维只能一个个删着试。

**v64 做了什么**：只去掉截断（`nanoTime()` 在同一 JVM 内单调递增，不截断就不会撞），
长度 30 < `varchar(32)`。这止住了血，但号变成了 19 位数字，人读不了。

**正解（未做）**：按日序列号，`ZC20260917-0001` 这种。需要：
- 一张按日计数的序列表或 Postgres 序列（**要新迁移**，v64 声明了无新迁移，故没做）；
- 并发下取号要么走序列、要么 `insert ... on conflict` 重试，不能用 `count(*)+1`（并发必撞）。

**为什么值得做**：资产编号是要印在资产标签上、盘点时人工核对的号。19 位随机数字等于没有编号规则，
一线盘点没法用；而这个号一旦发出去贴到设备上就改不了了，越早规范越好。

**顺带**：4091 是 `GlobalExceptionHandler` 对 `DataIntegrityViolationException` 的兜底，
它不说哪个约束。这类「唯一约束撞号」应当在业务侧捕获并给出可操作的话
（「资产编号重复，请重试」），否则每次撞号都是一次无法自助排查的报障。

## 全文检索端点接前端前的两条硬约束（v69 包 A 前置，已用例钉住）

`GET /api/cdr/search` 要接到患者全景的检索框上，接线前用 JUnit 实测出两条行为
（`Phase104CdrTest` 三条新用例，非推断）：

1. **空关键字匹配全部**——查询是 `like concat('%', :kw, '%')`，空串即 `like '%%'` 恒真。
   前端检索框清空后点检索，会拿回最近 50 份文档而不是空结果。**前端必须自己挡住空串**，
   不能依赖后端。
2. **关键字里的 `%` 与 `_` 是未转义的通配符**——用户输入单个 `%` 等于匹配全部。
   这不是注入（走的是绑定参数），但会让结果与用户预期不符。
   对照：平台别处的检索已有 `escapeLike` 的做法可复用。

另钉住：**单次最多返回 50 条**（端点内硬编码分页），前端不得把结果当全集展示，
须在界面上说明"最多显示前 50 条"，否则又是一处屏上假话。

## v141 IQC判定与最新列表回显归属

LisQcView对六字段IQC草稿和提交体分别快照，以保存、草稿、页面会话和身份判定当前单次结果；编辑/ABA、离开页签再返回、卸载或身份变化会清除并失效旧判定。只对POST未决期间的相同body本地去重，沿共享client原重复提示；不同body仍可并发，POST已决且刷新GET未决时相同body可再次正常追加。全项目/水平latest按独立GET代次、原页面会话及身份接收，编辑草稿不清空或筛选全局列表。同页同身份的任意已知成功POST仍可发一次新的真实全局刷新，旧判定失效不等于已保存事实回滚；已失效页面的旧续程不再夺读取权。
