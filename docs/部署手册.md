# HIP 平台生产部署手册

## 环境要求
- 服务器：2 台起（应用 + 数据库），4C8G 以上；操作系统 Linux（或信创麒麟）
- JDK 21（Temurin/信创 JDK）、PostgreSQL 16（或达梦/金仓 PG 兼容模式）、Node 仅构建期需要

## 部署步骤
1. **数据库**：`deploy/docker-compose.yml` 起 postgres+redis，或使用已有实例；创建库 `hip`、用户 `hip`
2. **后端**：`mvn clean package -DskipTests` 产出 `server/target/hip-server-*.jar`
   - 环境变量覆盖敏感配置：`SPRING_DATASOURCE_URL/USERNAME/PASSWORD`、`HIP_JWT_SECRET`（必须更换）
   - `java -jar hip-server.jar`（首次启动 Flyway 自动前滚至当前版本（含实施段 V10000+ 共存支持），并创建 admin/admin123——**上线立即改密**）
   - MLLP 设备接入端口 2575（`hip.integration.mllp-port`），防火墙仅对 LIS 网段开放；
     **pilot/prod 必须配置来源白名单 `HIP_MLLP_ALLOW`（逗号分隔，支持 CIDR 如 192.168.10.0/24），
     留空会拒绝启动监听（fail closed）**；不接检验设备则显式 `HIP_MLLP_ENABLED=false`。
     字符集按报文 MSH-18 自动识别（GBK/GB18030/UTF-8），单帧上限 1MB，连接数上限 `mllp-max-conn`（默认 16）
3. **前端**：`cd frontend/shell && npm ci && npm run build`，`dist/` 交给 Nginx：
   ```nginx
   location /api {
     proxy_pass http://127.0.0.1:8080;
     # 必配（1.1.0 起后端 forward-headers-strategy=framework 只认 X-Forwarded-*）：
     # 缺失时审计 client_ip 与门户登录锁定的来源 IP 恒为反代地址
     proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
     proxy_set_header Host $host;
   }
   location / { root /opt/hip/dist; try_files $uri $uri/ /index.html; }
   ```
4. **验证**：E2E 走环境变量，无需改脚本（测试库演练）：
   `HIP_E2E_BASE=http://<host>:8080/api HIP_E2E_USER=admin HIP_E2E_PASSWORD=<改后口令> python tools/e2e-outpatient.py`
   ⚠ 语义区别：`HIP_E2E_BASE` **含 /api**；下文 init-hospital 的 `--base` 传 origin **不带 /api**（脚本自拼）——两处混用是最常见的现场翻车点

## 运行态验收（1.2.6 补充，试点第一周必做）

- **巡检有效性**：`POST /api/ops/inspections/run`（ADMIN）手动触发一轮巡检，返回本轮开单数——
  不必等每小时 cron，装机当天即可验证"故障能被发现"。
  演练办法：故意把 `hip.ops.disk-paths` 指向不存在的路径 → 应开出 MEDIUM 工单；
  同题重复触发不应重复开单；工单处理后故障仍在则应重新开单
- **备份可恢复**：按「备份自动化」走完整演练（备份 → 恢复到校验库 → 逐表比对 → 恢复库跑 E2E）
- **错误码支持**：把 [错误码速查表.md](错误码速查表.md) 交给一线（按码查含义与处置）

## 安全基线（等保，产品化一期落地）
- **JWT 密钥**：设置环境变量 `HIP_JWT_SECRET`（≥32 位随机串，如 `openssl rand -base64 48`）；
  未设置时回落开发占位值——生产/试点严禁使用占位值
- **默认口令**：初始化用 `tools/init-hospital.py`（配置里 `adminNewPassword` 必填，
  执行末尾强制更换 admin 口令并验证）；**生产库严禁运行 `bootstrap-demo.py`**（演示账号 Demo1234）
- 密码策略 8 位字母+数字，5 次失败锁定 15 分钟；90 天更换提醒
- HTTPS：nginx 反代终止 TLS（`frontend/shell/nginx.conf` 基础上加 443 server 块与证书）
- 写操作全量审计（sys_audit_log），建议对接日志外发
- 患者端接口与院内接口角色级隔离（ROLE_PORTAL）
- **接口机账号一律用 INTERFACE 角色**（LIS/中间件 HTTP 接入）：安全链把它隔离在
  `/api/integration/**` 之内、无任何菜单——严禁给接口机 admin 凭据

## 医院初始化（产品化一期）
1. Flyway 随首次启动自动建库（自动前滚至当前版本，含平台必需与行业基线种子；1.1.9 起 out-of-order 已启用，支持实施段 V10000+ 与平台升级共存）
2. 复制 `tools/init-templates/hospital.example.json` 按院填写：院名、模块开关、科室病区床位、
   业务账号、字典 CSV（药品/收费项目/医保对照）
3. `python tools/init-hospital.py 配置.json --base http://<host>:8080`（幂等可重复）
4. 未采购模块在配置 `modules` 置 false——菜单与 API 双关闭（ModuleGate）

## 数据迁移
- 患者：`tools/import-patients.py`（模板 `tools/migrate-templates/patients.csv`，同证件号幂等）
- 药品/收费目录：init-hospital 字典 CSV 或 `POST /api/masterdata/drugs|charge-items/import`
- 医保对照：`POST /api/insurance/catalog/import`（模板 `tools/migrate-templates/yb-catalog.csv`）
- 在院患者重建（存量切换）：`tools/import-inpatients.py`（同证件号已在院幂等跳过，操作指南 §六.4）
- 老 HIS 历史文书：`tools/import-documents.py`（幂等键=类别+老单号，断点续跑覆盖更新；
  **不导则切换瞬间老病历对医生"消失"**，模板 `migrate-templates/legacy-documents.csv`）
- 老系统保留只读至少 1 年，切换演练至少 2 轮

## 回滚
- 应用：保留上一版 jar，直接替换回滚（Flyway 向前兼容，不自动降级——发版前备份库）
- **换包后必做**：`curl http://<host>:8080/actuator/info` 核对 `build.version`/`build.time`
  ——确认响应来自新（或回滚后的旧）产物，不要只看 health UP（彩排曾被未退出的旧进程假 UP 骗过）；
  发布打包用 `tools/release.py <版本>`，自带清单完整性校验（check_manifest）
- 数据库：每日 pg_dump 全量 + WAL 归档

## 部署形态定型（v17 试点收尾）

- **试点（本机/Windows）**：裸机形态——jar + WSL PostgreSQL + nginx，`spring.profiles.active=pilot`
  （application-pilot.yml：连接串/慢阈值/MLLP 均走环境变量，日志滚动 50MB×30）
- **院方服务器（Linux）**：deploy/docker-compose.full.yml 全栈（compose config 校验通过；
  CI 的 postgres 容器工作流即容器路径的持续验证）
- 两形态共用同一 jar 与 dist，仅编排差异

## 备份自动化（三十七期补充）

- 每日自动备份：管理员 PowerShell 执行 `tools\schedule-backup.ps1` 注册任务计划 `HIP-DailyBackup`（每日 02:30 调 `tools\db-backup.ps1`）
- 恢复演练：`tools\db-restore.ps1 -File deploy\backups\hip_xxx.dump`（默认恢复到校验库 hip_restore_check，不动生产库）
- **库名参数化**：`tools/db-backup.ps1 -Db <库名>`（默认 hip）——多院部署每院库名不同，
  务必按院传参，否则备的是另一个库
- **恢复验收判据**（1.2.6 演练升级）：脚本自检只看 sys_user 有行是不够的——
  须**逐表比对源库与恢复库计数**（患者/挂号/结算/医嘱/住院结算/flyway 版本），
  并**用恢复库启动一次应用跑 E2E**："能连上"不等于"可用"
- ⚠ **.ps1 编码纪律**：含中文的 PowerShell 脚本必须存为 **UTF-8 with BOM**——
  无 BOM 时 Windows PowerShell 5.1 按 GBK 解析，中文注释会破坏字符串终止符导致**脚本整体解析失败**
  （1.2.6 演练发现五个脚本全中招）。修改脚本后请确认 BOM 仍在
- 演示/验收数据：`python tools\bootstrap-demo.py`（幂等）
- 投标响应底稿：`python tools\export-deviation.py` → docs/验收/技术偏离表.csv

## 报表只读角色（1.0.6 起，DBA 一次性操作）

自定义报表引擎以只读角色执行，**角色不存在时报表拒绝运行**（安全兜底，不影响其他功能）。
应用账号通常无 CREATE ROLE 权限，故 V49 迁移尽力创建、失败不阻断，需 DBA 以超级用户执行：

```sql
create role hip_report_reader nologin;
grant usage on schema public to hip_report_reader;
grant select on all tables in schema public to hip_report_reader;
revoke select on sys_user, sys_config from hip_report_reader;   -- 口令散列与敏感配置不可读
grant hip_report_reader to <应用数据库账号>;                      -- 否则 set role 被拒
```

新增业务表后需补 `grant select`（或建 default privileges）。

## 附：数据库主备与故障切换（v28 演练验证）

单库部署满足试点，等保三级或对 RPO/RTO 有要求时按本节搭主备。
完整演练记录与命令见 docs/彩排与升级演练记录.md §九，此处为操作摘要：

1. **搭备库**：备机装同版本 PG16 → `pg_basebackup -h <主机> -U <replication用户> -D <数据目录> -R -X stream -c fast` → 起库后在主库 `pg_stat_replication` 确认 streaming
2. **主库故障切换**：停应用/摘流量 → 备库 `select pg_promote()` → 应用数据源改指备机 → 起应用 → E2E 冒烟（发布包自带 20 套）
3. **原主回归**：修复后的原主**重建为新主的备库**（不能直接回主），追平后择期计划内切回：停应用 → 干净停当前主 → promote → 应用切回
4. **纪律**：任何切换第一步停应用、最后一步起应用；切换后必跑冒烟；
   `show transaction_read_only` 可作应用侧「连到的是不是主库」的自检探针

## 附：admin 首登强制改密的置位说明（第六轮审阅 P2）

V61 里按 `password_updated_at = created_at` 给 admin 兜底置位的 UPDATE **恒不命中**
（两列由不同迁移事务的 now() 写入，必不相等）——该语句为死代码，因 Flyway checksum
锁定而保留原样，勿删改。实际行为：**任何库的 admin 都不会被自动强制改密**
（CI 处女库 E2E 依赖此行为，属有意取舍）。

试点交付需要 admin 首登强制改密时，实施人员手工置位：

```sql
update sys_user set must_change_password = true where username = 'admin';
```

或直接用 init-hospital.py 的第 7 步（自助路径改掉 admin123，改完即为最终口令，
不触发强制改密）。业务账号无此问题——管理员建号/重置口令即自动置位。

## 附：升级到含大表分区改造（V100）的版本前必读（第七轮审阅 P2）

v1.3.0 的 V100 迁移把 sys_audit_log / int_message_log / ops_slow_api 三张观测表改造为
按月分区表（建新表→整表复制→改名，单事务）。**实测**：2000 万行（约半年繁忙三甲的审计量）
单表复制+索引约 82 秒、产生约 4.9GB WAL，且在迁移提交前不释放。三表串行叠加，
数亿行规模可达 20–40 分钟纯停服 + 数十 GB WAL。

**升级前置（必做）**：
1. **先压量**：升级前对这三表按保留期归档/删除（审计留 180 天、其余 90 天之外的），把待迁移行数压到最小。
2. **预留磁盘**：数据盘与 pg_wal 各预留 ≥ 三表总大小的 2 倍余量（旧表+新表+WAL 峰值）。
3. **延长停服窗口预期**：按表数据量线性外推（约 4–5 分钟/亿行/表），不要按分钟级估。
4. **迁移中途"卡住"是正常的**（Flyway 跑在应用就绪之前）——**切勿误杀进程**，杀掉会整体回滚、前功尽弃且盘可能已被 WAL 占满。观察 pg_stat_activity 确认在推进。
5. 升级后确认三表 relkind=p（已分区）、_pdefault 分区为空、hip_purge_observability() 可手动执行。

> 运维长期纪律：hip_purge_observability 每日 03:00 补当月+2 月分区并清理过期分区。
> **该任务连续中断超 2 个月，新数据会落 default 分区、后续建分区将失败**——巡检已加「default 分区非空」告警。发现告警须尽快手工补分区。
