# 反驳者一（子要求拆解）

## 一、我的独立拆解（未参照审计者拆法之前的思路）

参数原文：「拥有处方、检验单、检查单、治疗单、导诊单打印功能。」——这是一条**存在性**条款（"拥有...功能"），不是"完备性/合规性"条款。我认为紧扣字面的子要求应当是：对 5 类单据分别成立的一组横切检查，而不是把每种"打印功能的行业延伸做法"都拆成独立子项。

**紧扣字面（判定用）**：
- A 类：5 种单据各自能生成有内容的可打印页面（非空白、非占位符）。
- B 类：5 种单据各自在真实业务操作路径中存在可达入口（不是只有后端接口）。
- C 类（横切）：角色权限不阻断合理使用者。
- D 类（横切）：无数据/异常时不崩溃、有合理提示。

**行业默认外延（观察项，不直接决定"有没有功能"）**：
- 打印预览、批量打印、重打留痕/补打检索、条码图形化、按单据号单选打印。这些是"打印功能做得多完备"，不是"有没有打印功能"。参数原文没有一个字提到留痕、批量、条码，不能反向要求。

**处于中间地带、我认为需要单独判断的一项**：
- 打印出来的纸面内容是否与医嘱录入内容一致（即"有值印值"）。这不是纯粹外延——如果一张"检验申请单"打印出来后系统性地不反映医生填的检查目的/标本要求等，这已经不是"打印功能不够完备"，而是"打出来的东西是假的"，理论上可以质疑"打印功能"本身的诚信度。但我认为**这项要求的达标责任应归属于催生这些字段的具体条款**（v44 引入的 remark/urgent/clinical_summary/exam_purpose/notice/specimen_type/sampling_site 七个字段，代码注释明确标注对应 1006★/1013★/1014★/1016★），而不是 1026★ 本身——1026★ 字面只要求"拥有...打印功能"，没有列出必须印哪些字段。这与审计者的处理不同（见下）。

## 二、与审计者拆解的差异

1. **章节语境判断，我的论证比审计者更硬**：审计者只说"检验单/检查单读作申请单"是"判断……可争议"。我用 CSV 原文核对了 1018、1020 两行——这两行在同一批门诊/检验相关条款里，**明确使用"报告调阅""图文报告查看"字样**来表达"结果类"概念。1026 与处方、治疗单、导诊单并列，这三者无一例外都是"医生开出、患者/科室带着走"的单据，而不是"结果回传"的单据；且本表在需要表达"报告"时从不吝惜使用"报告"二字。既然 1026 没有用"报告"，只用"单"，我认为"检验单/检查单=申请单"这一读法证据充分，不是审计者所说的"可争议"，而是**站得住的主读法**。因此由此派生的 #2b（检验报告单入口）、#3b（RIS 检查报告零打印）不应作为阻断 1026 上调的硬缺口——它们对应的是另一个（较弱的）候选读法。

2. **#15（v44 七字段未上纸）的归属，我与审计者有分歧**：审计者把这条列为"打回点 2"，视为很有分量的阻断理由。我认为这混淆了条目责任——这七个字段是否要在纸面呈现，是 1006★/1013★/1014★/1016★ 的达标范围，不是 1026★ 字面写明的东西。1026★ 只要求"拥有打印功能"，不要求"打印内容包含所有医嘱扩展字段"。这条问题客观存在（见下方核实），但我不把它算作 1026 的推翻理由。

3. **我发现审计材料本身有一处证据性错误**：审计材料开头只标注了 2 个"工作区未提交"文件（`LisView.vue`、`DoctorStationView.vue`），但 `git status` 实际显示 **5 个前端文件**被修改，还有 `PrintView.vue`、`RisView.vue`、`RegisterView.vue`。其中 **`PrintView.vue` 的工作区改动恰恰直接推翻了审计者自己在 #15 给出的"全文 grep 零命中"证据**——当前工作区版本对"检验申请单""检查申请单"两个分支已经消费了 urgent/remark/clinical_summary/notice/specimen_type/sampling_site/exam_purpose 六到七个字段（逐字段核验见下表）。审计者的 #15 证据对**当前工作区**不成立，应是针对 HEAD 或历史缓存跑的 grep。

4. **外延项分类上，我与审计者结论一致**：#9（留痕）、#10（单选打印）、#11（批量）、#14（条码图形）我也认为不构成字面推翻理由，这与审计者"总判定"部分的处理一致，只是我认为这几条应从"子要求判定表"里挪到"完备性观察项"，不与真正的字面子项混排，避免误导后续复核者把它们当成阻断依据。

## 四、结论

**结论：不推翻，但须在说明中标注以下保留项。**

理由：参数字面「拥有处方、检验单、检查单、治疗单、导诊单打印功能」是存在性条款。5 类单据在当前工作区状态下均有：可用的生成内容、两条独立可达的业务入口（门诊医生站/门诊收费台）、恰当的角色权限、合理的异常处理，以及控制器级自动化测试覆盖——这一层没有找到"参数字面要求 + 代码确实没有"的硬缺口。审计者提出的三个"最可能打回点"逐一核验：(1) 检验单/检查单读作报告单的替代解读，经我用 1018/1020 两行原文比对后判定站不住，主读法（申请单）成立；(2) v44 字段未上纸的问题，工作区当前版本已对检验/检查申请单基本修复，且该达标义务本就不属于 1026★（属于 1006★/1013★/1014★/1016★ 另案）；(3) 留痕/批量/条码等属行业默认外延，参数原文未作要求，不能反推为字面缺口。三点均不足以构成推翻。

**保留项清单（不推翻，但上调说明落地前应处理/如实注明）**：
1. 我核验用到的关键证据——`PrintView.vue` 对 v44 字段的消费、`LisView.vue`/`DoctorStationView.vue` 的检验报告单打印入口、`RegisterView.vue` 的挂号凭条入口——**均是工作区未提交改动**（`git status` 显示 5 个前端文件为 M，非全部已提交）。若在 HEAD（当前 tag v1.6.5）状态下复核，检验申请单/检查申请单不会显示这些新字段，检验报告单/挂号凭条也没有前端入口。**上调前必须先提交这批改动**，否则判定与实际发布版本不符。
2. 治疗单（治疗单打印）仍未消费 v44 七字段（remark/urgent/clinical_summary/notice 等），后端已返回该数据但前端 treat-sheet 分支未取用——建议在 1006★/1013★/1014★/1016★ 的复核中单独跟踪，不要遗漏。
3. 现说明文字（CSV 中 1026 行，本次核验未见改动，仍是 v43 前的旧措辞）若要改写为「正偏离/无偏离」，务必：① 把"检验单/检查单"明确写成"检验申请单/检查申请单"，避免读法歧义被抓；② 不要写成"已提供检验报告单打印能力"这类会被对照到 RIS 报告零打印按钮（#3b 硬缺口，只是不适用于本条）而产生自相矛盾的措辞；③ 如实注明批量打印、补打留痕、条码图形化、按单据号单选打印等为后续增强项，不写成"打印中心功能完备"式的过度宣称。
4. 审计材料自身有一处证据性瑕疵需要更正：其"工作区未提交改动"清单遗漏了 `PrintView.vue`/`RisView.vue`/`RegisterView.vue` 三个文件，且 #15 给出的"全文 grep 零命中"证据对当前工作区不成立（该文件工作区版本已消费 6-7 个字段）——这不影响本次"不推翻"结论，但审计材料本身需要修订以免误导后续车道。
