## 1006★ → 落库回显链核对表 / 口径问题 / 结论

### 独立核对（超出审计材料的新发现）

**处方笺（`prescription`）打印模板完全不渲染 RX 行的 `remark`/`urgent`，尽管数据全链路齐全。**

- 医生站「处方」页签已给 RX 行加了「加急」复选框与「备注」输入框：`frontend/shell/src/views/outpatient/DoctorStationView.vue:311-316`
- 后端逐行落库：`modules/outpatient/.../DoctorStationService.java:773-774`（`o.setRemark(line.remark())` / `o.setUrgent(...)`），对全部 `order_type` 一视同仁，无 DRUG 例外
- 打印数据集 `DOC_ORDER_SQL` 对全部单据类型统一取 `o.remark, o.urgent`：`server/src/main/java/cn/hip/server/web/PrintReportController.java:180`，处方笺请求同样命中这条 SQL（`DOC_ORDER_TYPE.get("prescription")="DRUG"`，见 `:136-140`）
- 但 `frontend/shell/src/views/PrintView.vue:168-193`（`type === 'prescription'` 分支）从 `Rp.` 到签名栏，逐字核对**没有任何一处**引用 `r.remark` 或 `r.urgent`；对照同文件 209/236/271 行，lab-request/exam-request/treat-sheet 三个模板都用 `<span v-if="r.urgent">...</span><span v-if="r.remark">...</span>` 渲染了同一批字段，`.urgent`/`.remark` 的 CSS（564-565 行）也是为这三张单据定义的，唯独处方笺一张都没接
- 复现条件：医生在处方行填"过敏体质，缓慢滴注"之类的备注并勾选加急 → 提交处方 → 打印「处方笺」→ 纸面上这条备注和加急标记**完全消失**，药师拿到的处方笺上看不到医生写的这句话

1006 参数字面要求的是"录入功能"，本条不因此推翻"RX 行已有备注录入"这一子判定；但它印证了上一轮 1026★ 被推翻的同一类问题——**字段存在、后端也在下发，但落在最终被别的岗位（这里是药师）使用的那张纸上时凭空消失**，"备注功能"对处方笺这个最常用的单据类型而言是有输入、无回显，价值打了折扣，应作为保留项写入复核意见，防止评审自行打印验证时当场发现。

### 独立核对（复核确认审计材料的关键证据）

- 逐一核对住院侧：`frontend/shell/src/views/inpatient/InpDoctorView.vue` 全文件搜索 `remark|备注|注意事项|notice` **零命中**；`grep -rn "remark" server/src/main/resources/db/migration/*.sql | grep -i inp_order` 同样**零命中**。审计材料给出的"住院医嘱全链路无备注/注意事项能力"这一最核心的反驳点经独立复核完全成立，未发现任何遗漏的分支或后续迁移把这个缺口补上。

### 判定

**不推翻审计者"不建议整体上调为已完全提供/正偏离"的结论，且追加一条独立保留项。**

一句理由：参数写的是"**所有**医嘱"，而住院医嘱（`inp_order`）从 UI 到数据库列全链路仍是零覆盖，且门诊侧唯一有完整闭环的 RX 备注/加急连自家处方笺都印不出来，两条独立证据都指向"未完全提供"，维持部分响应级别，不支持上调。

## 1013★ → 落库回显链核对表 / 口径问题 / 结论

### 独立核对（对审计材料两条保留意见的裁定）

**保留意见 #6a（加急标志检验科不可见）：经核对，工作区未提交改动已经修复，但尚未提交。**

`git diff -- frontend/shell/src/views/medtech/LisView.vue` 显示新增了「申请信息」列，把 `row.urgent`（红色「加急」标签）、`row.specimen_type`/`row.sampling_site`、`row.remark` 一并显示在"待采样"与"标本工作队列"两张表里。字段来源核对：`modules/medtech/.../MedTechController.java:91`（`lisPending`）与 `:140`（`samples`）两条 SQL 本就 select 了 `o.specimen_type, o.sampling_site, o.urgent, o.remark`，前端字段名与 SQL 输出列名逐字对应，绑定正确，不存在"取错列"的问题。**若这次改动被提交**，审计材料列出的"反驳者最可能打回的三点"之第 2 点（加急是死信息）即告解除，构成开单端→数据库→打印→检验科工作台的完整闭环，这条应视为支持上调的加分项。

**遗留的次要口径缺口（新发现，不足以否决上调，但应披露）**：`lisPending`/`samples` 两条查询仍是 `order by o.id` / `order by s.id`，加急标志现在"可见"了，但队列本身**不按加急排序、不提供筛选**，检验科要在整屏列表里肉眼找红标。参数原文只要求"加急标志录入功能"，不要求排序，故这点不构成推翻理由，只作为完整性备注。

**保留意见 #9（"检验项目诊断"逐项 vs 整单口径分歧）：经核对，代码层面无法裁决，维持为未解决的解释风险。**

复核 `DoctorStationView.vue:356-368` 的"申请信息"列确认 LAB 分支只有 `specimenType`/`samplingSite` 两个输入框，没有任何逐项诊断字段；`V137__outp_order_fields.sql:34-36` 的开发者自述原文"不做'检验项目诊断'的独立列……再建一列会出现两份可以互相矛盾的诊断"属实，是开发方单方面选定的解释，非甲方原始定义。这一条无法靠补代码解决，是纯文义风险。

### 判定

**不推翻，但须标注两项保留（一项程序性、一项解释性）。**

一句理由：加急标志录入→持久化→打印→（若改动落地则）检验科可见，四段链路数据绑定经独立核对全部正确，支持审计者"上调到基本响应/正偏离"的建议；但（1）修复检验科可见性的三个文件是未提交的工作区改动，必须先按车道纪律提交才能作为定版证据，否则评审依据的已提交代码仍是"加急录了但检验科看不到"的旧状态；（2）"检验项目诊断"逐项/整单的解释分歧是开发方自定口径，应在复核意见中原文披露，不能证据不足就默认对己方有利的解释。

### 独立核对（对审计材料两条保留意见的裁定）

### 判定

**不推翻，但须标注两项保留（一项程序性、一项一致性）。**

一句理由：临床摘要/检查目的/注意事项三项子要求的"录入→持久化→打印→技师站可见"链路经独立核对完整且字段绑定正确，支持把说明文字从"全部未提供"改写为"三项已提供、诊断资料复用既有模块"；但（1）承载这一改善的三个文件仍是未提交状态，须先提交定版；（2）`lab-request` 模板遗留的 `clinical_summary`/`notice` 手填栏缺口说明这批修复未覆盖到姊妹单据，"诊断数据资料未设专属录入点"这条审计者已指出的字面缺陷依旧成立，不支持把 1014 整体判为完全响应。

## 1016★ → 落库回显链核对表 / 口径问题 / 结论

### 独立核对

审计材料的三条保留意见——①"自动获取"只发生在打印页而非开单界面本身、②"根据流向"被 `md_charge_item.exec_dept_id` 这个静态字典外键偷换、③`clinical_summary` 列注释同时挂 1014/1016 造成误判风险——逐条复核代码：

- ①：`DoctorStationView.vue:339-385`（"检查检验"页签）确认医生提交申请那一步界面上不展示 `briefHistory`/`diagText`，这两个 computed 只存在于 `PrintView.vue:398-402` 与 `:395-396`，只在打印预览页触发。属实，且工作区未提交的三处改动**都没有触碰这一点**——LIS/RIS 新增列显示的是 `urgent`/`specimen_type`/`sampling_site`/`remark`/`exam_purpose`/`clinical_summary`/`notice`，不包含"病情摘要/诊断在开单当下可见"这件事，这条保留意见原样成立，未被本次工作区改动解决。
- ②：`platform/masterdata/src/main/java/cn/hip/platform/masterdata/web/MasterDataController.java:247-251` 确认 `exec_dept_name` 来自 `md_charge_item.exec_dept_id` 的静态 left join，无任何按标本条件、患者信息、当日排班计算路由的逻辑；`:240` 处的注释"exec_dept 即 1016★『按流向自动取执行科室』的数据来源"是开发者自我认定，不是第三方定义。这是本轮四条里**证据最硬、最不受工作区改动影响**的一条口径问题：字面"流向"暗示动态判断，实现是逐项目固定配置，两者不是同一件事，若响应说明照抄参数原文"根据流向自动获取执行科室"，构成对评审的误导性陈述。
- ③：`V137__outp_order_fields.sql:50` 的列注释与 `addLabLine()`（`DoctorStationView.vue:1329-1334`，只初始化 `{orderType, itemId, itemName, category, qty}`）经独立核对，确认 `clinical_summary` 确实没有"由病历自动带入"的任何逻辑，纯手敲，且只绑定在 EXAM 分支——LAB 类订单永远拿不到这一列。此为文档与代码不符的注释误导，非功能缺陷，但足以让评审顺着注释去找一个不存在的能力。

工作区未提交的改动虽然让 LIS 界面显示了 `specimen_type`/`sampling_site`（子要求③④，本就判定符合），但**没有改变**①②③三条保留意见涉及的任何一处代码路径，因此 1016 的裁定不受本次未提交改动影响。

### 判定

**不推翻，维持审计者"部分符合，不建议整体上调为符合/正偏离"的结论。**

一句理由：子要求③④（标本类型/采样部位）录入-持久化-打印-检验科可见链路完整可判"已提供"，但"按流向自动获取执行科室"经核对是逐项目固定字典外键、不含任何动态路由判断，与参数原文"流向"一词的字面含义存在实质性偏差，这条不是解释分歧而是**行为与用词不符**，是本轮四条里唯一一条建议明确写入复核意见、要求响应说明改用"按项目字典预设执行科室"而非"根据流向自动获取"表述的条目。
