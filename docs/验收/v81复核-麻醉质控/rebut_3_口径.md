## 四、4910 / 4911 边界与「不以建单为下界」裁定

- **4911 下界裁定：合理，但须在说明里写清。** 手术申请没有独立的「申请时刻」字段（只有建单时刻），申请本身也常事后补录，以建单为下界会挡掉合法补录；`sys_audit_log` 留有每次取消请求的登记人与登记时刻（实测两条 `PUT …/42/cancel` 均在库），补录的取消时刻可追溯。代价是取消可以回填到任意已结账的历史期（实测回填到 2020-01-01 成功并计入当日），说明里不应写「系统限定取消时刻范围」之类的话。
- **4910 修补不完整（N4）**：分段文档写「申请阶段须未排台、排程 / 入室前须未入室、术中须已入室」，代码字面照此实现；但这三条规则挡不住审计原样复现的「已入室已开台记申请阶段取消」（未带排台时间的台次只查 `scheduled_at`），`docs/下一步开发规划.md:10` 举的例子「如已入室却登记『申请阶段取消』」在未排台时并不报 4910。`V81SurgeryCancelGuardTest` 只测了「已排台 → APPLY」「已入室 → SCHEDULE/PRE_IN」「未入室 → IN_OP」，三个缺口都没有用例。建议补修：APPLY 另须未入室、未开台；SCHEDULE / PRE_IN 另须未开台；IN_OP 须已入室或已开台；已出室（或已结束）的台次不收「术中取消」或取消时刻不晚于出室。
- **文案一致性**：`docs/错误码速查表.md:407-408` 的 4910 / 4911 与源码一致（4910 只抓到前缀「取消阶段与已登记时间点不一致：」，生成器限制，可接受）；`docs/错误码分段.md:48` 的 4910 / 4911 与代码一致，但 **4909 仍写「两条路径同码」**，现已有第三条（取消时刻解析失败，`SurgeryService.java:294`），速查表已列三条，分段文档未跟（N11）。

## 六、须标注句（逐句草稿，可直接写入说明）

### 1424★（N1 修复后适用；未修则加第 1 句括注）
1. 「首台」指同一手术间同一日内最早入室的一台已开展手术（已登记开台时间或已完成）；未登记入室时间的按开台时间排序，未登记手术间的台次不参与首台统计。（N1 未修时加：日期按开台时间归属，零点后开台的手术归入开台当日。）
