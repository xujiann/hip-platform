# 虚拟医院全量彩排与升级演练记录（2026-08-07，v1.0.0 定版依据）

> 一手记录整理自提交 5f51a80（v17 A3+C）。本记录是「标准产品 + 实施个性化」闭环成立的验收证据，
> 教材第 14 章案例框引用；后续医院实施可按同法自验。

## 一、虚拟医院全量彩排（模拟一次完整实施）

**目的**：用一次彻底的假实施证明四层模型闭环——标准产物不动、全部差异落在配置/适配器/impl。

**环境**：全新空库 `hip_rehearsal`（与开发库完全隔离），标准发布产物。

| 步骤 | 内容 | 结果 |
|---|---|---|
| 1 装机 | 空库启动，Flyway 一次前滚 44 个迁移（含 V10000 实施段） | 通过 |
| 2 初始化 | init-hospital 改院名『彩排第二医院』、建科室病区床位账号、强改 admin 口令 | 通过（幂等复跑验证） |
| 3 模块开关 | 关 blood/surgery 两模块 | 菜单消失 + API 404 双路实测，恢复后复原 |
| 4 impl 定制 | impl/template-hospital 模板模块实跑（ping + notes 写读，V10000 段建表） | 通过 |
| 5 适配器替换 | 假省 SDK 医保适配器以 @Primary 替换 Mock | 20 条 fake-sdk 报文留痕、YBSDK 结算号回填，业务与对账零感知 |
| 6 全量回归 | **19 套 E2E 在彩排实例全量执行** | 全部通过 |

**结论**：标准产品可在不改动核心代码的前提下完成一次完整「新院实施」。
彩排临时挂载 impl 的 pom 改动已还原——标准根 pom 不含 impl（ADR-0003 规约）。

## 二、N-1 → N 升级演练

**目的**：验证操作指南 §三升级流程（停服→备份→换产物→自动前滚→回归抽查）真实可执行。

**环境**：`hip_drill` 库。

| 步骤 | 内容 | 结果 |
|---|---|---|
| 1 | 部署 N-1 版（V42 产物，worktree 检出构建）并造业务数据 | 就绪 |
| 2 | db-backup 全量备份 | 备份文件可用（恢复演练另见部署手册） |
| 3 | 替换 N 版产物重启 | Flyway V43 自动前滚 |
| 4 | 验证 | 旧数据完好、新配置就位、接口正常 |

**结论**：升级窗口内无需人工干预数据库；失败路径为备份恢复回滚（未触发）。

## 五、已装 impl 的库做平台升级（2026-08-17，1.1.9 B-13 补课）

**背景**：第四轮审阅发现 impl V10000+ 与 Flyway 默认 `outOfOrder=false` 相撞——医院库最高版本
到达 V10000 后，平台下一版的新迁移（版本号 < 10000）会被判乱序、**升级直接拒启**。
此前两次演练恰好都测不到：装机演练是空库按序全量、升级演练的库没装 impl。

**演练**（hip_drill2 全新库）：
1. 阶段一：V1–V56 + `V10000__impl_drill_demo.sql`（模拟已实施医院）→ 57 个迁移全过，
   `flyway_schema_history` 最高版本 10000，应用健康
2. 阶段二：换含 V57/V58 的新版产物再次启动 → 两个新平台迁移以 **`[out of order]`** 标记
   成功前滚（`Successfully applied 2 migrations ... now at version v58`），应用健康

**前提修复**：`application.yml` 增 `spring.flyway.out-of-order: true`（平台段 V1–V999 与
实施段 V10000+ 版本号不相交，乱序风险可控）；ADR-0003 同步补注。

**过程教训（记录在案）**：第一次跑阶段二时端口被未退出的阶段一进程占用，健康检查 UP
是旧进程的假象——**验证升级必须确认响应来自新产物**（后改前台带 timeout 运行并核对
flyway_schema_history）。这条同样适用于真实医院升级验收：换包后 curl /actuator/info
比对构建时间（1.1.9 起产物内置 build-info）。


## 六、跨大版本升级：v1.0.0 → v1.2.4（2026-08-20，v23 方向 A）

**为什么补这一场**：零到一装机（§一）、已装 impl 的库升级（§五）都演练过，
但"**老版本医院升到当前版**"从未验证——而这正是第一家试点医院日后每次升级要走的路。
v1.0.0（V43）到 v1.2.4（V59）之间 16 个迁移含大量存量敏感变更：
唯一索引预清洗（V52）、列改 text（V55）、结算单号方案切换（V54）、部分索引与状态过滤。

**演练（全新库 hip_upg，全程用发布包产物而非源码）**：

1. `release/hip-platform-1.0.0/hip-server-1.0.0.jar` 装机 → `now at version v43`
2. 造老版业务数据：老包自带 E2E 跑门诊闭环（含退费）+ 手工造一笔住院出院结算
   → 老版单号 `CY20260820-000001`（**纯数字尾**，正是 1.1.8 撞号事故的原始形态）
3. 升级前基线：3 患者 / 2 挂号 / 4 结算 / 4 医嘱 / 1 住院结算 / V43
4. 停旧实例 → `release/hip-platform-1.2.4/hip-server-1.2.4.jar` 同库启动
5. **结果：16 个迁移全部前滚成功，`now at version v59`**，`/actuator/info` 自报 `1.2.4`
   （1.2.4 修复的版本自证在真实升级路径上生效）

**升级后验收**：

| 检查项 | 结果 |
|---|---|
| 数据完好 | 3/2/4/4/1 **一行不差** |
| V50 回填 | `refunded_at` 已回填 2 张历史退费单 |
| 新旧单号共存 | 老 `-000001` 与新 `-S000002` 同日不撞（`S` 区分符实证生效） |
| 新功能可用 | 结算冲销（1.1.3 新增，老版没有）→ 患者恢复 IN_HOSPITAL → 重结 `-S000003` |
| E2E 冒烟 | 发布包 e2e-outpatient 对升级后实例通过 |

**过程发现并修复**：发布包只带 `e2e-outpatient.py` 一套 E2E——实施方拿包**做不了完整验收**
（住院/医保/集成等 19 套缺失）。release.py 改为全量 20 套 + e2elib 入包（1.2.5）。

**结论**：跨大版本升级路径可用，试点医院的升级动作有了实证依据。
升级验收步骤见部署手册「回滚」节（换包后必查 /actuator/info）。

## 七、运行态演练：故障注入 + 备份恢复（2026-08-20，v24 方向 A/B）

**为什么补这一场**：代码正确性（五轮审阅）与部署工艺（装机/impl/跨版本升级）都已实证，
但"医院跑起来之后"从未端到端验过——故障怎么被发现、备份能不能真恢复。
这两件事在试点第一周就会被检验。

### A 故障注入（自动巡检有效性）

演练库 hip_ops，故意配 `--hip.ops.disk-paths=/nonexistent-volume-test`：

| 注入的故障 | 巡检结果 |
|---|---|
| 24 小时内无成功备份 | ✅ 开 HIGH 工单 |
| 磁盘监测路径不存在 | ✅ 开 MEDIUM 工单 |
| 慢接口超阈值（灌 60 条） | ✅ 开 MEDIUM 工单 |
| 重复巡检 | ✅ 开单数 0（同题不重复开） |
| 工单处理后故障仍在 | ✅ 重新开单（不会永久静默） |

**过程改进**：巡检原先只有 cron 一条触发路径——试点现场"巡检到底有没有在工作"
无法当场验证，只能等一小时或翻日志。新增 `POST /api/ops/inspections/run`
手动触发并返回本轮开单数（1.2.6）。

### B 备份恢复（数据安全最后一道）

**演练前先撞到两个致命缺陷（备份脚本此前根本跑不起来）**：

1. **所有含中文的 `.ps1` 是 UTF-8 无 BOM** → Windows PowerShell 5.1 按 GBK 解析，
   中文注释破坏字符串终止符 → `db-backup.ps1` / `db-restore.ps1` / `schedule-backup.ps1`
   等五个脚本**全部解析失败**。这意味着 v1.0 之后备份从未真正可用过（当时演练环境编码不同）。
   修：五个脚本统一加 UTF-8 BOM。
2. **Windows 路径传给 wsl 时反斜杠被吞**（`C:Usersdrxuj...`）→ wslpath 必失败，
   备份走不到拷贝步。修：在 PowerShell 侧算好 `/mnt/<盘符>/...` 路径再传。
3. 顺带：`-Db` 参数化（原硬编码 `hip`，多院部署每院库名不同，备的永远是另一个库）。

**修复后完整演练**：

| 步骤 | 结果 |
|---|---|
| 造数据（门诊+住院 E2E） | 4 患者 / 2 挂号 / 4 结算 / 4 医嘱 / 1 住院结算 |
| `db-backup.ps1 -Db hip_ops` | ✅ 450 KB dump 落盘 |
| `db-restore.ps1 -TargetDb hip_restore_check` | ✅ 恢复成功 |
| **逐表比对源库 vs 恢复库** | ✅ 七项计数完全一致，flyway 版本同为 V59 |
| **恢复库启动 + E2E** | ✅ 应用 UP，门诊闭环 E2E 通过——数据在且业务能跑 |

判据升级：原脚本自检只看 `sys_user > 0` 行，本次改为**逐表比对 + 恢复库跑 E2E**——
"能连上"不等于"可用"。

## 八、多实例部署演练（2026-08-27，v27-D）

**背景**：调度锁（advisory lock）与业务抢占（条件更新）声称支持多实例，
但功能完成度矩阵边界 ④ 如实标注"多实例部署未做过完整演练"。本轮补上。

**方式**：两个实例（8080 / 8081）同连 `hip_demo` 库，第二实例启动时 Flyway
校验通过直接就绪（同库共存无迁移冲突）。探针脚本四步实证：

| 探针 | 结果 |
|---|---|
| JWT 跨实例复用 | A 实例签发的 token 在 B 实例直接可用——无状态签名，**多实例无需会话粘滞**，前置负载均衡可用普通轮询 |
| 同一就诊跨实例并发结算 10 次（A×5 + B×5） | 成功 **1**、抢占拒绝 **9**——条件更新抢占在 DB 层，跨实例天然成立（实证而非推断） |
| A 实例退费 × B 实例发药并发 | 恰好一方成功（退费成功、发药被拒）——跨业务竞态互斥跨实例成立 |
| 并发触发两实例巡检（注入故障） | **A 开 1 张工单、B 开 0 张**——advisory lock 互斥 + 工单幂等双防线 |
| E2E 打 B 实例全链路 | 门诊闭环（含退费/医技执行）全部通过 |

**结论**：矩阵边界 ④ 关闭。多实例横向扩展的三个前提（无状态认证、DB 层抢占、
调度互斥）全部实证成立。前置 nginx 轮询即可组双活；数据库仍是单点，
高可用需另行规划主备（超出本轮范围，如实标注）。
