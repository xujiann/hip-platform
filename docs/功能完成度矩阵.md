# HIP 平台功能完成度矩阵（v1.2.12，2026-08-27）

> 与 `docs/功能清单.md` 的分工：功能清单答**"有什么"**（面向选型沟通），
> 本矩阵答**"做到什么程度"**（面向实施排期与验收）。
> 全部数字由源码实测，不取印象值；复算命令见文末附录。

## 一、完成度分级口径

平台各域的成熟度差异是真实存在的，笼统说"已完成"会误导实施排期。本矩阵按四级标注：

| 级别 | 含义 | 判据（须全部满足） |
|---|---|---|
| **A 业务闭环** | 有状态机、并发防线、事务边界，可直接上生产 | 服务层承载业务规则 + 条件更新/原子操作 + 单测 + E2E 闭环 |
| **B 完整功能** | 功能齐备、有校验，但业务规则相对线性 | 有 E2E 覆盖主流程 + 关键校验有测试 |
| **C 台账报表** | 建档、登记、统计、导出为主，规则薄 | 有 E2E 冒烟，CRUD 与查询完整 |
| **D 接入点就绪** | 平台侧完成，等外部资质/SDK/硬件 | SPI 定义 + Mock 实现 + 生产闸门 |

**C 级不是"没做完"**——医院信息化中台账与统计类模块本就以数据完整性和报表口径为主，
过度设计状态机反而增加实施负担。分级是为了让实施方知道**哪些域需要重点验收并发与异常路径**。

## 三、A 级域的并发正确性实证（试点验收重点）

A 级的判据里最硬的一条是并发防线**被实际撞过**，而非只是写了条件更新。当前状态：

| 抢占点 | 防的事故 | 实证方式 |
|---|---|---|
| `claimCharge` | 双结算 / 双倍扣款 | 六线程真并发，1 成功 5 拦下 |
| `claimDispense` | 双发药 / 库存双扣 | 六线程真并发 + 库存终值断言 |
| `claimRefund`（明细） | 钱已退、药也发了 | 退费 × 发药跨业务竞态互斥 |
| `claimRefund`（单据） | **重复冲正医保额度** | 六线程 × 三轮 + **不依赖时序的确定性断言** |
| `claimCancel` | 结算冲销双提交、重复冲正医保额度 | 六线程真并发 + 确定性断言（1.2.9 补） |
| `claimReadmit` | 一张床挂上两个住院档 | 随冲销并发验证「恰好召回一次」 |
| 库存回补 | 退药双回补 | `StockRestoreConcurrencyTest` 真提交模式 |

> **本矩阵自身产出的第一个结果**：编制过程中发现住院侧 `claimCancel`/`claimReadmit`
> 此前**只有单线程功能测试**，却被按 A 级列出——按新口径这不成立，已当场补上六线程
> 真并发与确定性断言（实证通过：住院侧实现本就正确，缺的是证据而非防线）。
>
> **1.2.9 的教训写进了口径**：单据级抢占此前只有住院侧有，门诊退费漏了——
> 而本地六线程测试恒定"1 成功 5 拦下"，看起来完全正常，CI 上才暴露六方全放行。
> 因此本矩阵对 A 级的要求已升级为：并发用例须**跑多轮**或**另配不依赖时序的确定性断言**。
> 详见 `docs/测试方法论.md` 第 ⑨ 条。

## 五、诚实标注的边界

矩阵的价值在于把"没做的"也写清楚。当前明确边界：

1. **C 级域的业务规则由实施期配置补足**——HRP 与数据治理提供的是台账、流程留痕与
   报表引擎，各院的审批链与考核口径差异极大，平台不预设
2. **模块开关按注册表收口，未注册模块不受开关管辖**——开关三路生效（菜单过滤 +
   API 前缀 404 + insurance 业务码拦截），v27 扩至 8 个 key 并补 insurance 只读豁免
   （停用后历史分割/对账仍可查，冲销依据不失）。`/api/inpatient/**` 等前缀被
   医技/质控多模块共享，结构上不能整段收口——扩新 key 须逐一核对前缀独占性
   （侦察结论存档于本轮规划 v27-B）
3. ~~患者模糊名搜百万级~~ **已关闭（v27-C）**：V60 pg_trgm GIN 后百万级实测
   精确号 115ms→0.11ms、三字名 54ms→0.34ms；残余为二字词无命中 ~104ms（如实标注，不再优化）
4. ~~多实例部署未演练~~ **已关闭（v27-D）**：双实例同库实证 JWT 跨实例复用、
   跨实例抢占恰好一方成功、巡检不重复开单、E2E 经任一实例通过
   （docs/彩排与升级演练记录.md §八）。**数据库仍是单点**，高可用需另行规划主备
