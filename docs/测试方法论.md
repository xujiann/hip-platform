# 测试方法论（八条，用实付学费换来的）

> 每条都对应一次真实翻车。新测试/新验证动作前过一遍本清单；
> 违反任何一条的"绿"都可能是假绿。接手者读这份，不必读会话记忆。

## ① 安全闸门必须在真实部署路径上验证，且有自动化覆盖

1.0.6 的 JWT 密钥闸门与 Mock 适配器门禁绑定 pilot/prod profile，而 compose 与 CI 都不设
profile——按文档部署的系统两道闸门全部跳过，清单标 ✅ 而实际从未执行过。
现状防线：CI `pilot-guard` 作业逐条冒烟两道闸门。

## ② 改并发/失败路径必须验证"修复后的失败路径"

1.0.8 的预约重试循环写在 `@Transactional` 内——PG 唯一冲突后事务已 aborted，重试必 500，
修复从未生效且把"两人同号"换成"500"。只验证正常路径会让错误的修复看起来是对的。
范式：可编程假适配器定向让渠道失败 → 断言全量回滚 + 重试安全（Phase116ChannelOrderTest）。

## ③ 权限收紧后必须验证每个角色仍能用系统

1.0.9 权限批让方法级拒绝变 401，前端判"登录过期"清 token——护士登录即被踢出，
20 套 E2E 全绿因为都用 admin。现状防线：Phase110RoleUsabilityTest 七角色逐一
"能登录、能开首页"；新角色（如 INTERFACE）要加"进得来该进的、进不来其余全部"两向断言。

## ④ `@Transactional` 测试里回滚不会发生

assertThrows 接住异常后，事务作为参与者**不回滚**（异常没穿出事务边界）——
"抛异常即回滚"的断言在事务测试里是假绿。回滚语义必须真提交模式验证
（弃用 @Transactional、多线程各自提交，见 StockRestoreConcurrencyTest 注释）。
同理：@Transactional 单线程测不了并发（ConcurrencyFixTest 类注释有警示）。

## ⑤ 事务内直写 sys_config 会给 ConfigReader 缓存下毒

直写配置 → ConfigReader 读入缓存 → 测试事务回滚 → **缓存仍带毒**污染后续测试。
直写配置的测试类须 `@AfterEach` `configReader.evictAll()`（ModuleGate 同理 evictCache）。

## ⑥ 升级验收必须确认响应来自新产物

B-13 演练曾被未退出的旧进程假 UP 骗过。换包后 `curl /actuator/info` 比对
`build.version`/`build.time`（release 包已内置且 permitAll），不要只看 health UP。

## ⑦ 改动共享患者/共享数据的 E2E 后，必须在全新库按 CI 顺序全量复跑

phase3 的 INP_SUMMARY 断言曾隐式依赖 e2e-inpatient 恰好用患者 2 入院——消除硬编码后
CI 处女库断裂，本地历史库完全掩盖。本地复现法：建 hip_ci 空库 + CI 同款 prep 脚本 +
`.github/workflows/ci.yml` 同顺序跑 20 套。

## ⑧ 现场包括时间：本地北京时区测不出 UTC runner 的日窗口错位

v1.2.1 CI 在 UTC 22:40（北京 06:40）打红：测试/E2E 用 runner 本地日期、
PGJDBC 又把 JVM 时区设为会话时区，日窗口整体偏 8 小时。
现状防线：`connection-init-sql` 钉死会话时区、`BusinessDates.today()`/`today_bj()` 统一取数、
**CI 有意保持 UTC 作为常驻时区金丝雀**——本地复现法 `mvn test -Duser.timezone=UTC`。

## ⑨ 并发测试要证明"真的发生了竞争"

多线程测试一次就绿是可疑信号：可能压根没形成竞争（线程串行执行），
此时"只有一方成功"是平凡成立的假绿。**除断言成功数，还要断言失败数**——
`Phase128ClaimConcurrencyTest` 对六线程抢占断言 `失败数 == THREADS - 1`，
若为 0 说明没形成真竞争，测试本身失效。

同时：抢占失败必须是**可读业务异常或锁冲突**，不能是裸 500/约束错——
用户看到的应是"请刷新后重试"，而不是"系统内部错误"。

**并发测试的"绿"与机器强相关**（1.2.9 实证）：门诊退费缺单据级抢占，本地六线程恒定
"1 成功 5 拦下"（先行者已提交、后来者读到新状态），CI 上六方同时读到旧状态**全部放行**。
故并发用例要么**跑多轮**把偶发变必现，要么**另配一条不依赖时序的确定性断言**
（如"对已退单据再抢占必须返回 0 行"）——后者才是真正锁住防线的那一条。

**推论：只读校验一律前置于抢占**。抢占在前时，业务校验失败也已改了状态——
生产上事务回滚无碍，但 @Transactional 测试里不回滚（第 ④ 条），会把后续断言带偏。
并发安全由抢占的行数判定保证，与校验先后无关，故校验前置无损防线。

**MockMvc + 手设 SecurityContext 必须跨请求清理**（第六轮实证）：残留登录态让
JwtAuthenticationFilter 的外层门（getAuthentication()==null）不成立，整个 token 解析
与兜底闸被跳过——测的是残留态而非 token 链，"闸没生效"其实是测试假象。与第 ④ 条同源。

## 配套纪律（一句话版）

- 全新库验证：`wsl -d Ubuntu -u postgres -- psql -c "create database hip_xxx owner hip;"`，
  起应用完成迁移后再灌数/走查
- 多模块改动必须全量 `mvn clean install`；**打包前先停占用 jar 的进程**（否则 repackage 静默失败跑旧码）
- WSL 空闲关机会带走 PostgreSQL：测试 0 秒全挂先查库，保活 `wsl -d Ubuntu -- sleep 28800 &`
- 种子数据是测试契约：替换 B 类种子前看 docs/种子数据分层清单.md「测试契约」节
- 新错误码先登记 docs/错误码分段.md；新配置键先补 docs/配置手册.md 并进 validate
