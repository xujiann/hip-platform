# 多医院部署操作指南（v1.3，2026-08-17）

> 读者：实施工程师。前置阅读：docs/产品化方案.md（四层模型）、docs/部署手册.md（单机细节）。
> 形态铁律：**一院一实例一库**，全部医院使用**同一个标准发布产物**；医院差异只存在于
> 配置（L2）、适配器实现（L3）、impl 定制模块（L4）。标准核心永不分叉。

## 一、部署形态与资源要求

每院独立部署（院内网），一台应用服务器即可起步：

| 组件 | 要求 | 端口 |
|---|---|---|
| 应用（server jar） | Java 21（Temurin） | 8080 |
| 数据库 | PostgreSQL 16，独立库 | 5432 |
| 前端 | nginx 托管 dist + 反代 /api，TLS 终止 | 80/443 |
| MLLP 监听（接检验设备） | 可选，`hip.integration.mllp-enabled` | 2575 |
| ai-service | 可选（缺席自动降级） | 8100 |

两种装机方式二选一：`deploy/docker-compose.full.yml` 全栈容器，或裸机（jar + nginx + 系统 PostgreSQL）。

## 二、单院部署七步（每家医院重复执行）

### 第 1 步 · 装机
1. 生成并设置 JWT 密钥（**必做**）：环境变量 `HIP_JWT_SECRET`（≥32 位随机串，`openssl rand -base64 48`）
2. 建空库（owner 授给应用账号），启动应用——Flyway 自动建 V1-V43 全部结构与 A/B 类种子
3. nginx 挂前端 dist、反代 `/api`、配置 TLS

### 第 2 步 · 初始化（init-hospital）
1. 复制 `tools/init-templates/hospital.example.json`，按院填写：
   - `hospital.name` 院名（前端/打印/患者端全联动）
   - `modules`：未采购模块置 false（DRG/CDSS/医保/用血/人事/手麻——菜单与 API 双关闭）
   - `depts`：门诊科室 + 病区（`type: NURSING` 带 `beds` 数自动建床）
   - `accounts`：业务账号与角色
   - `adminNewPassword`：**必填**，工具末步强制更换 admin 口令并验证
2. 执行：`python tools/init-hospital.py <院配置>.json --base http://<host>:8080`（幂等可重复）
3. **该院配置 JSON 存入实施资料库**（每院一份，是重装与审计的依据）

### 第 3 步 · 字典与数据迁移
| 数据 | 途径 | 模板 |
|---|---|---|
| 药品目录 | init 配置 `drugsCsv` 或 `POST /api/masterdata/drugs/import` | tools/init-templates/drugs.example.csv |
| 收费项目 | 同上 charge-items | charge-items.example.csv |
| 医保对照 | `POST /api/insurance/catalog/import`（管理页有对照率统计） | tools/migrate-templates/yb-catalog.csv |
| 存量患者 | `python tools/import-patients.py`（同证件号幂等） | migrate-templates/patients.csv |
| 在院患者（存量切换） | `python tools/import-inpatients.py`（§六.4，已在院幂等跳过） | migrate-templates/inpatients.csv + inpatient-orders.csv |
| DRG 目录 | 官方目录整表替换 drg_group_def/drg_cc_list 后 regroup-all | — |

### 第 4 步 · 接口适配（各省各院差异所在）
先填**接口现状调研表**（医保/LIS 设备/PACS/CA/支付商与联系人），再按 SPI 对照实施：

| 差异点 | 接入点 | 约定 |
|---|---|---|
| 医保 | InsuranceAdapter（换省 SDK 实现 Bean） | **ADR-0002**（结算号回传/留痕关键字/失败语义） |
| 聚合支付 | PayAdapter | 同构留痕 |
| CA 签名 | SignatureAdapter | 病历签名冻结语义不变 |
| 检验设备 | MLLP 2575（须配 `HIP_MLLP_ALLOW` 来源白名单）/ HTTP ORU（INTERFACE 角色凭据） | HL7 V2 ORU^R01；字符集按 MSH-18（GBK/GB18030/UTF-8） |
| AI | ai-service HTTP（可缺席） | 平台侧优雅降级 |

未到位的适配器保持 Mock——业务闭环完整可用，对接后无缝切换。
同省同商的适配器实现包**跨院复用**，放实施仓库统一维护。

### 第 5 步 · 真定制（如有）
按 **ADR-0003**：复制 `impl/template-hospital` 为 `impl/<hospital>`，V10000+ 迁移段、
`impl_` 表前缀、`/api/impl/**` 路由。实施仓库根 pom 挂载；标准仓库不动。

### 第 6 步 · 制度化运行
- 备份：`tools\schedule-backup.ps1` 注册每日任务（02:30），按 `db-restore.ps1` 做一次恢复演练留档
- 告警：运维中心健康阈值核对（磁盘/备份时效/慢接口）
- 医保：每日自动对账默认开启（01:30，差异自动开故障工单）

### 第 7 步 · 培训与试运行
- 按 docs/培训脚本.md 跑 8 角色 + 患者端真人培训
- 验证：`python tools/e2e-outpatient.py`（指向该院测试库演练）
- 试运行问题一律进运维中心故障工单台账，按第四节「分层归位」处置

## 三、多院并行管理（车队管理）

### 版本策略
- 所有医院运行同一标准产物；实施资料库维护**装机登记表**：院名 ｜ 版本 ｜ 配置 JSON ｜ 适配器实现及版本 ｜ impl 模块 ｜ 联系人
- 新版本发布后**逐院滚动升级**，先升试点院观察再推其余

### 升级流程（每院独立执行，约 15 分钟停机窗口）
```
停服 → 备份库(db-backup) → 换 jar+dist → 启动(Flyway 自动前滚) → 回归抽查(核心 E2E) → 失败则备份恢复回滚
```
配置、字典、规则库、impl 段迁移全在数据库里，产物替换动不到它们（四层模型的升级红利）。
有 impl 模块的医院：升级前先在实施仓库对新版重编译 impl，编译失败即兼容性破裂信号，先修再上。

### 问题分层归位（运行期铁律）
每个反馈先判层再动手：**改配置（当场生效）→ 换数据/规则（当场生效）→ 适配器缺陷（改实现包，同省同修）→
平台缺陷（提产品需求进版本，所有医院受益）→ 真定制（进该院 impl 模块）**。禁止为单院改平台核心。

## 四、上线前检查清单（逐项打勾）

- [ ] `HIP_JWT_SECRET` 已设置（非开发占位值）
- [ ] `SPRING_PROFILES_ACTIVE=pilot` 生效（缺密钥/带 Mock 时启动必须失败——两道闸门实测各拦一次）
- [ ] 数据库 `show timezone` 为 Asia/Shanghai（夜间任务与归档判断同时区）
- [ ] init-hospital 执行成功，admin 口令已更换（admin123 登录须返回 1001）
- [ ] 未采购模块已关闭（直连 API 实测 404）
- [ ] 字典导入完成，医保对照率达标（管理页可查）
- [ ] 生产库**未**运行过 bootstrap-demo（无 Demo1234 账号）
- [ ] 备份任务计划已注册且完成一次恢复演练
- [ ] HTTPS 生效；8080/5432 不对院外网开放
- [ ] 8 角色账号各登录一次，菜单与其职责相符
- [ ] 接口调研表归档；已接适配器跑通对账/回传实测（对账须含**金额比对**用例：改一分钱须出差异）
- [ ] MLLP 若开启：`HIP_MLLP_ALLOW` 已按 LIS/中间件实际 IP 配置（pilot 下留空会拒绝启动监听）；
      从白名单外主机连 2575 实测被拒
- [ ] 接口机账号使用 INTERFACE 角色（严禁给 LIS 中间件 admin 凭据）
- [ ] 无权账号访问受限接口后，`sys_audit_log` 有对应 403 记录（等保"失败访问留痕"抽查）
- [ ] 出院结算冲销（出院召回）流程已对住院收费员培训（结算错误不再允许改库）

## 五、常见问题

| 现象 | 处置 |
|---|---|
| 启动即失败 | 查 Flyway 日志；确认库空或版本连续；实施段仅允许 V10000+ |
| 登录 401/1001 | 口令已被 init 更换，用配置里的新口令；连错 5 次锁 15 分钟 |
| 某模块整页消失 | 检查 `module.*.enabled` 配置——可能实施时按未采购关闭 |
| 医保对账有差异 | 看故障工单差异单号；核对适配器留痕是否符合 ADR-0002 关键字约定 |
| 检验结果未自动回传 | 集成监控查 ORU 报文；MLLP 端口连通性；OBR-2 须为申请单号 |
| 升级后 impl 接口报错 | 实施仓库对新版重编译 impl 模块，按 ADR-0003 修兼容 |

## 六、存量医院切换（替换在用 HIS）

第二节七步针对新装；医院已有信息系统正常运行时，在七步之上叠加本节。
增量难点只有两件事：**历史数据策略**与**切换日处置**。

### 6.1 总原则

- **历史不迁账**：财务与医保账以切换日为界，HIP 从零起记——日结、对账、医保申报从第一天就是干净口径
- **老系统降只读**：保留 1-3 年查询入口供追溯历史费用与病历；老系统是历史数据的权威来源，不做二次搬运
- **业务单轨**：不搞长期双轨双录入；老系统仅在切换后 2 周内保持可写待命（回退预案），之后降只读
- **唯一必须迁的业务数据是在院患者**（见 6.4）；其余在途业务在老系统收敛闭环

历史病历若临床强烈要求随诊可查：按院写抽取脚本将老系统历史文书**只读入 CDR 文档层**
（进患者 360 时间轴，不进业务表），属 impl 定制（V10000 段）——评估工作量后再承诺。

### 6.2 时间线（在七步基础上）

| 时点 | 动作 |
|---|---|
| T-4 周 | 完成七步的 1-4 步（装机/初始化/字典/接口调研）；与医保经办约定切换日 |
| T-2 周 | 全员培训完成；老系统导出四类字典做**编码映射表**归档；停止放切换日之后的预约号源 |
| T-1 周 | 存量患者索引导入（import-patients，幂等可反复追跑）；医保目录对照率达标；切换演练一次（测试库全流程） |
| T-3 天 | 在途业务收敛：催结未收费处方、未取药在老系统闭环；在院患者清单冻结核对 |
| T-1 天 | 库存实物盘点；老系统中期结算试算 |
| **T 日** | 选月初结账后低峰日执行 6.3 清单 |
| T+2 周 | 无重大故障则老系统降只读；实施资料库归档切换记录 |

### 6.3 切换日检查清单（顺序执行）

- [ ] 老系统门诊/入院登记停用（挂号收费转 HIP）
- [ ] 在院患者：老系统逐一中期结算（费用截断），结算单存档
- [ ] 在院患者在 HIP 重建入院（见 6.4），床位与实际逐一核对
- [ ] 押金余额按老系统结算单转入 HIP（入院押金）
- [ ] 期初库存：按盘点表以药库入库单录入（备注「期初」，留盘点表编号）
- [ ] 医保：切换日起在 HIP 发起结算；老系统医保通道停用
- [ ] 患者索引抽查 20 例（证件号/姓名/性别与老系统一致）
- [ ] 上线前检查清单（第四节）复核一遍
- [ ] 当晚：HIP 首次日结试跑；备份任务确认执行

### 6.4 在院患者重建（最费人工的一步，必须提前演练）

老系统中期结算后，用 **`tools/import-inpatients.py`** 按病区批量重建：
入院登记占床 + 押金余额转入 + 自动写「迁移备注」病历（留档原住院号）+ 可选长期医嘱重开
（医嘱 CSV，仅对本次新建的住院执行，防重复计费）。**幂等**：同证件号患者已在院整行跳过，可反复补跑。
模板：migrate-templates/inpatients.csv（老住院号/姓名/证件号/科室/病区/床号/诊断/押金余额）+
inpatient-orders.csv（类型 DRUG/ITEM，项目名称须与字典完全一致）。
前置：患者索引先经 import-patients 导入；床位状态须 FREE（先在 HIP 建好床位）。
护理级别/风险评估补录仍为人工。切换前在测试库演练计时——按床日估算人手与切换窗口。

### 6.5 回退预案

T+2 周内出现不可当日修复的重大故障：老系统恢复可写，HIP 停止收新业务；
HIP 已记业务（切换日至回退日）导出留档，故障修复后按 6.3 重新切换。
回退决策人与判断标准（如：收费中断 >2 小时）在切换方案中**事先书面约定**。

### 6.6 与新装的差异汇总

| 事项 | 新装 | 存量切换 |
|---|---|---|
| 患者索引 | 随到随建 | T-1 周批量导入 + 切换日抽查 |
| 在院患者 | 无 | 中期结算 + HIP 重建（6.4） |
| 库存 | 首次入库即期初 | 盘点后期初入库 |
| 医保 | 直接联调 | 与经办约定切换日，双系统不并行申报 |
| 历史数据 | 无 | 老系统只读 1-3 年；可选历史文书入 CDR（impl） |
| 回退 | 无 | 2 周老系统可写待命（6.5） |

### 6.7 老系统数据获取策略（原厂商不配合时）

原则：**不需要"库结构"，需要"医院自己的数据"**——库结构/程序可主张商业秘密，
数据归医院（《电子病历应用管理规范》；数据安全法框架下医院为数据处理者）。按层推进：

| 层 | 途径 | 要点 |
|---|---|---|
| 1 商务 | 查老合同"数据字典/配合迁移"条款；维保续费/尾款/履约金谈判窗口 | 替换决定公开**前**谈，公开后筹码贬值 |
| 1' 利益兼容 | 不要库结构，按**迁移清单**让厂商交付 CSV，付迁移配合服务费 | 行业常态，几千到几万级，多数僵局在此解 |
| 2 标准化出口 | 医保接口/病案首页上报(HQMS/DRG)/互联互通测评文档库(CDA)/LIS·PACS 对接视图/传染病直报 | 政策逼开的门，厂商拦不住；测评材料即"字典说明书" |
| 3 技术自查 | 医院机房医院服务器，信息科凭 DBA/OS 权限连库：information_schema 反查、界面操作+审计日志定位表、数据采样对照界面 | **只读数据，不逆向程序**（反编译/绕加密授权触红线）；数据被加密存储→回第 1/2 层，"医院读不到自己的数据"在卫健层面即有力主张 |
| 4 兜底 | 患者列表/在院一览/字典维护页的**界面导出与报表打印**，人工整理成 CSV | 历史不迁账原则下必迁清单很小，几千条两三天 |

进场第一周三线并行：查合同条款 ＋ 盘点第 2 层出口（最快最省钱）＋ 评估信息科库权限；
调研结果填接口现状调研表"老系统数据出口"页。`import-*` 工具链全部吃 CSV——
不管从哪层拿到表格，都能迁。

**防止 HIP 成为下一个钉子户**：HIP 实施合同应主动写入
"数据归医院所有；无条件配合数据迁移；交付数据字典（Flyway 迁移脚本即全量结构，本身开放）"
——既是给院方的信任状，也是本产品的立场（四层模型：配置与数据全在库内，可自行导出）。
